1. Conceptos fundamentales utilizados

El frontend es una aplicación de una sola página construida con React 19 y Vite 8, que consume la API REST del propio proyecto. No accede nunca a la base de datos: pide y envía datos por HTTP, y es el backend quien decide qué se puede hacer.

Componentes, props y composición

Cada pieza de interfaz es una función que devuelve JSX. Lo que cambia entre usos llega por props: TarjetaContenido recibe el título, el detalle y el tipo de bloque, y decide con una condición si se dibuja como enlace o como texto. Así la misma pieza sirve para los seis bloques del perfil sin repetir código.

Estado y efectos

useState guarda lo que cambia mientras la pantalla está abierta y avisa a React de que debe volver a dibujar. useEffect sirve para lo que ocurre fuera del dibujado —pedirle los datos al servidor— y su lista de dependencias decide cuándo se repite: con [dias], solo al cambiar el periodo de las estadísticas.

Cada efecto que pide datos devuelve una función de limpieza. Sin ella, si se consulta un negocio y antes de que llegue la respuesta se consulta otro, la primera podría pisar a la segunda.

Dos peticiones en desarrollo no son un error. StrictMode ejecuta cada efecto dos veces a propósito, para que salte a la vista un efecto que no sabe limpiarse. En producción se ejecuta una sola vez.

Contexto

La sesión —quién eres, tu rol, entrar y salir— vive en un contexto (AuthContext) en lugar de pasarse por props de pantalla en pantalla. Al abrir la aplicación no se confía en lo que hay guardado en el navegador: se le pregunta al servidor con GET /usuarios/me, de modo que un token caducado o revocado se detecta enseguida.

Enrutado y rutas protegidas

React Router decide qué pantalla se dibuja según la dirección. RutaProtegida exige sesión y, cuando hace falta, un rol.

El guardia no es seguridad. Quien escriba la dirección a mano o llame a la API con curl se lo salta entero. La seguridad la aplica Express en cada endpoint: una cuenta de empresa recibe 403 aunque consiga pintar la pantalla. Lo que hace el guardia es no ofrecer puertas que van a dar error.

Separación en capas

Ninguna pantalla llama a fetch. Todas pasan por un servicio, y todos los servicios por un único apiClient que pone la dirección base, el tipo de contenido y el token, y convierte un error del servidor en una excepción con su mensaje. Si mañana cambia la forma de autenticarse, se toca un archivo.

2.2 Por qué cada decisión

Componente Justificación
apiClient Única puerta de salida hacia la API. El ejemplo de la guía comprueba body.success; esta API no tiene ese campo, y fiarse de él haría que todo pareciera correcto. Manda el código HTTP.
AuthContext La sesión la necesitan la barra, el guardia y cuatro pantallas. Pasarla por props obligaría a atravesar componentes que no la usan.
RutaProtegida Un solo sitio donde se decide quién pasa. Recuerda a dónde iba el usuario para devolverlo ahí después de entrar.
CampoTexto Las cuatro pantallas de cuenta repetían el mismo bloque de etiqueta, campo y texto de ayuda.
GraficaActividad SVG dibujado a mano, sin librería: son dos series de entre siete y noventa puntos, y traer chart.js con react-chartjs-2 costaría 70 KB comprimidos —la aplicación pasaría de 98 a 169, un 72 % más—, medido instalándolos y compilando. El <title> de cada punto da la información al pasar el cursor, que es cosa del navegador.
DetalleCuenta Va en un <dialog> para que el navegador se encargue del foco, de Escape y de bloquear lo de detrás.
TablaUsuarios Bajo 780 px cada fila se convierte en una ficha con el nombre de la columna delante de su valor. Una tabla de siete columnas en un móvil obliga a desplazar la pantalla a lo ancho para alcanzar los botones.

3. Evidencia de integración con la API

El frontend consume 38 de los 40 endpoints de la API REST del proyecto. Los dos restantes son GET /api/health, que solo comprueba que el servidor responde, y POST /api/publico/:slug/eventos, que registra los escaneos y las visitas: lo llama la vista pública que sirve Express, no esta aplicación, porque si lo hiciera inflaría las estadísticas cada vez que el dueño abriera su propio panel.

5.3 Defectos encontrados y corregidos

Construir estas pantallas destapó cinco defectos, cuatro en el propio frontend y uno en el backend. Se documentan porque forman parte del proceso:

Defecto Causa y corrección
Un botón se publicaba como texto (backend) El tipo se decidía comparando el nombre de la categoría con el literal 'Botón', y el cliente mysql de la consola de Windows reescribía los acentos al cargar las migraciones. Se corrigió con SET NAMES utf8mb4 en los dieciséis archivos SQL y comparando por el icono, que es ASCII.
Nombres de columnas en la API (backend) GET /usuarios devolvía las filas tal como salen de MySQL mientras el resto respondía en camelCase. Nadie lo veía porque el frontend original no llama a esa ruta.
El diálogo se cerraba solo close() dispara el evento close, que borraba el estado; y StrictMode ejecuta el efecto dos veces. La limpieza sobraba.
El arrastre fallaba al ser rápido El índice de origen iba en estado de React, que no se ha aplicado cuando llega el drop si los tres eventos caen en el mismo tic. Se pasó a useRef.
La barra se quedaba con el nombre viejo Al cambiar el nombre, la barra seguía mostrando el anterior hasta recargar. AuthContext gana un refrescar().

5.6 Dos cosas que estas pruebas no demuestran

Se dicen porque callarlas sería justamente el tipo de error que estas pruebas existen para evitar.

El arrastre rápido no se puede reproducir aquí. El defecto era una carrera: los tres eventos del arrastre caen en el mismo tic y el estado de React todavía no se ha aplicado. Pero fireEvent envuelve cada evento en act(), que vacía la cola de React, así que la carrera no llega a darse: se comprobó volviendo a poner el useState, y las dieciséis pruebas seguían en verde. En su lugar se mide con un Profiler que empezar un arrastre no provoque un redibujado, que es lo que distingue una ref del estado, y esa sí falla con el código viejo.

El destino recordado al entrar tampoco. Por el mismo act(), el <Navigate> de «ya tienes sesión» le gana al navegar(desde) y la pantalla acaba en la portada. Se comprobó en un Chromium de verdad, contra los dos servidores: entrar en /contenido sin sesión e iniciarla aterriza en /contenido. La prueba afirma por eso a dónde manda la pantalla, no dónde acaba.

5.7 Lo que este frontend todavía no tiene

No hay pruebas de extremo a extremo propias, en un navegador de verdad. El frontend original del proyecto tiene 396 de Playwright y este se verificó pantalla por pantalla a mano contra el servidor real, pero las dos comprobaciones de la sección anterior enseñan dónde está el límite de jsdom: lo que depende del momento exacto en que React aplica un cambio pide un navegador.
