1. Conceptos fundamentales utilizados

El frontend es una aplicación de una sola página construida con React 19 y Vite 8, que consume la API REST del propio proyecto. No accede nunca a la base de datos: pide y envía datos por HTTP, y es el backend quien decide qué se puede hacer.

Componentes, props y composición

Cada pieza de interfaz es una función que devuelve JSX. Lo que cambia entre usos llega por props: TarjetaContenido recibe el título, el detalle y el tipo de bloque, y decide con una condición si se dibuja como enlace o como texto. Así la misma pieza sirve para los seis bloques del perfil sin repetir código.

Estado y efectos

useState guarda lo que cambia mientras la pantalla está abierta y avisa a React de que debe volver a dibujar. useEffect sirve para lo que ocurre fuera del dibujado —pedirle los datos al servidor— y su lista de dependencias decide cuándo se repite: con [dias], solo al cambiar el periodo de las estadísticas.

Cada efecto que pide datos devuelve una función de limpieza. Sin ella, si se consulta un negocio y antes de que llegue la respuesta se consulta otro, la primera podría pisar a la segunda.

Dos peticiones en desarrollo no son un error. StrictMode ejecuta cada efecto dos veces a propósito, para que salte a la vista un efecto que no sabe limpiarse. En producción se ejecuta una sola vez.

Contexto

La sesión —quién eres, tu rol, entrar y salir— vive en un contexto (AuthContext) en lugar de pasarse por props de pantalla en pantalla. Al abrir la aplicación no se confía en lo que hay guardado en el navegador: se le pregunta al servidor con GET /usuarios/me, de modo que un token caducado o revocado se detecta enseguida.

Enrutado y rutas protegidas

React Router decide qué pantalla se dibuja según la dirección. RutaProtegida exige sesión y, cuando hace falta, un rol.

El guardia no es seguridad. Quien escriba la dirección a mano o llame a la API con curl se lo salta entero. La seguridad la aplica Express en cada endpoint: una cuenta de empresa recibe 403 aunque consiga pintar la pantalla. Lo que hace el guardia es no ofrecer puertas que van a dar error.

Separación en capas

Ninguna pantalla llama a fetch. Todas pasan por un servicio, y todos los servicios por un único apiClient que pone la dirección base, el tipo de contenido y el token, y convierte un error del servidor en una excepción con su mensaje. Si mañana cambia la forma de autenticarse, se toca un archivo.

3. Evidencia de integración con la API

El frontend consume 39 de los 40 endpoints de la API REST del proyecto. El que falta es GET /api/health, que solo comprueba que el servidor responde.

POST /api/publico/:slug/eventos —el que cuenta escaneos, visitas y clics— lo llama solo la página del código QR, /p/:slug. El panel del dueño no, o inflaría sus propias estadísticas cada vez que abriera su perfil. La diferencia no se ve en pantalla: equivocarse ahí no rompe nada, solo deja las cifras mintiendo, y por eso tiene pruebas propias.

5.3 Defectos encontrados y corregidos

Construir estas pantallas destapó cinco defectos, cuatro en el propio frontend y uno en el backend. Se documentan porque forman parte del proceso:

Defecto Causa y corrección
Un botón se publicaba como texto (backend) El tipo se decidía comparando el nombre de la categoría con el literal 'Botón', y el cliente mysql de la consola de Windows reescribía los acentos al cargar las migraciones. Se corrigió con SET NAMES utf8mb4 en los dieciséis archivos SQL y comparando por el icono, que es ASCII.
Nombres de columnas en la API (backend) GET /usuarios devolvía las filas tal como salen de MySQL mientras el resto respondía en camelCase. Nadie lo veía porque el frontend original no llama a esa ruta.
El diálogo se cerraba solo close() dispara el evento close, que borraba el estado; y StrictMode ejecuta el efecto dos veces. La limpieza sobraba.
El arrastre, que resultó no estar roto El índice de origen se pasó a useRef creyendo que con estado el arrastre rápido fallaba. Medido después en Chromium —ver 5.6—, no falla: React aplica el cambio de dragstart antes de entregar el drop. La ref se queda porque ahorra un redibujado; la explicación que la acompañaba era falsa y se corrigió.
La barra se quedaba con el nombre viejo Al cambiar el nombre, la barra seguía mostrando el anterior hasta recargar. AuthContext gana un refrescar().

5.6 Dos cosas que estas pruebas no podían demostrar

Las dos salían del mismo sitio: fireEvent envuelve cada evento en act(), que vacía la cola de React entre uno y el siguiente. Eso esconde todo lo que dependa del momento en que React aplica un cambio. Las dos se resolvieron midiéndolas en un navegador de verdad, y ninguna acabó donde se creía.

El arrastre rápido. Se daba por hecho que los tres eventos caen en el mismo tic y que con el índice de origen en estado el arrastre fallaba. No falla: se midió cambiándolo a useState y arrastrando en Chromium, despacio y con los tres eventos uno detrás de otro, y reordena igual, porque React trata dragstart y drop como eventos discretos y aplica el cambio antes de entregar el siguiente. La ref se queda porque ahorra un redibujado de la lista entera por cada arrastre que empieza —eso sí lo mide un Profiler—, no porque haga falta. El comentario del componente, que afirmaba una carrera inexistente, se corrigió.

El destino recordado al entrar. Aquí no era una limitación de las pruebas: era un defecto. Está en 5.8, porque lo encontró la suite de extremo a extremo y es el motivo de que exista.

Las dos afirmaciones estaban escritas en el código, en este documento y en el README, y las dos eran falsas. Se corrigen donde estaban, y no solo aquí: una explicación equivocada que sobrevive en un comentario es la que leerá quien toque ese archivo dentro de seis meses.

5.7 El frontend publicado

Desde la versión v3.3.0 es este el frontend que sirve el servidor: abrir la dirección del proyecto entrega esta aplicación, y los códigos QR llevan a su página /p/:slug. El original sigue en el repositorio y se publica cambiando una variable, FRONTEND=clasico; sus 396 pruebas de Playwright pasan igual, porque levantan su propio servidor.

Publicarlo obligó a tres cosas que no hacían falta con el original, y que son las que de verdad distinguen servir una aplicación de una sola página:

Qué hubo que hacer Por qué
Reenviar las rutas al index.html /perfil o /contenido no son archivos: los resuelve el enrutador en el navegador. Sin esto funcionan al navegar y dan 404 al recargar, que es el fallo más fácil de dejar pasar. Solo se reenvían los GET sin extensión: a un POST a una ruta que no existe hay que decirle que no existe, y a un .js que falta, también.
Inyectar las etiquetas de vista previa WhatsApp, Telegram y Google no ejecutan JavaScript, y esta pantalla se dibuja entera en el navegador: sin inyectarlas en el servidor no habría nada que leer al pegar el enlace. El index.html lleva las mismas marcas que usaba la pantalla del frontend original.
Mover el enlace del correo React no sirve archivos .html: la recuperación de contraseña apunta ahora a /restablecer. La dirección sale de la configuración y sigue a la variable, porque escribirla en el servicio la habría dejado desfasada al cambiarla.

Y una pantalla nueva, /p/:slug, que es la que ve quien escanea: sin buscador —ya llegó a su negocio— y con el registro de escaneos, visitas y clics que hasta ahora hacía el frontend original.

Un defecto encontrado al probarlo. La primera versión guardaba en una ref que ya había contado la visita, para que StrictMode no la contara dos veces. Sobraba —la bandera de vigencia del efecto ya lo impedía— y además dejaba sin contar la visita al ir de un negocio a otro dentro de la aplicación, porque React Router reutiliza el componente cuando solo cambia el slug. La prueba que lo destapó falla con la ref y pasa sin ella.

5.8 Las pruebas de extremo a extremo

129 pruebas en 7 archivos, con Playwright sobre Chromium, contra el paquete compilado. Se ejecutan con npm run test:e2e: compilan la aplicación, la sirven y la apagan al terminar, y no necesitan ni el backend ni MySQL.

Existen por lo que dice 5.6. Las 439 de Vitest corren en jsdom, que no es un navegador: no aplica CSS, no tiene arrastre nativo, no descarga archivos, no tiene sendBeacon, no tiene historial ni pestañas, y envuelve cada evento en act(). Aquí no se repite nada que jsdom pueda contestar: solo lo que necesita un navegador.

Archivo Qué prueba Por qué no en jsdom

arrastrar (12) Reordenar arrastrando, despacio y con los tres eventos seguidos; las flechas con ratón y teclado jsdom no tiene arrastre nativo ni dataTransfer

Las dos últimas corren además con el viewport de un teléfono, porque en una pantalla estrecha cambian el contraste de algunos fondos, el orden visual y el tamaño de lo que hay que pulsar.

Encontraron tres defectos en su primera ejecución. Es la razón de ponerlas, y la medida de lo que las 439 anteriores no alcanzaban a ver:

Defecto Qué pasaba y cómo se corrigió
El destino recordado al entrar no funcionaba Quien abría un enlace a /contenido sin sesión entraba y aterrizaba en la portada. La pantalla de login tenía dos salidas: el <Navigate> de «ya tienes sesión» y un navegar(state.desde) después del await. En el navegador ganaba la primera —React agrupa el setUsuario con lo que viene detrás, dibuja una sola vez y desmonta la pantalla—, y el navegar() llegaba sobre un componente desmontado, que React Router ignora en silencio. Ahora hay una sola salida, declarativa.
Las flechas de reordenar medían 22 x 20 px Por debajo de los 24 x 24 que pide el criterio 2.5.8 de la WCAG 2.2, y son la única forma de reordenar con el dedo, porque el arrastre de HTML no funciona al tacto. Se les puso un mínimo de 32 px.
La etiqueta del rol no tenía contraste Blanco al 75 % sobre el índigo de la barra da 4,27:1, y hace falta 4,5:1 para texto pequeño. Salía en las nueve pantallas que llevan la barra. Subida al 85 %: 5,00:1.
El primero es el que importa. La prueba de Vitest no podía verlo, y el comentario que acompañaba al código afirmaba —sin haberlo medido— que en el navegador funcionaba bien. Una suite que no puede fallar donde el código está roto no es una red de seguridad: es una afirmación sobre el código escrita en otro sitio.

La API se simula dentro del navegador, con memoria: reordenar y volver a pedir la lista devuelve el orden nuevo, como haría el servidor. Sin esa memoria, una prueba de reordenar pasaría aunque la pantalla no mandara nada. Y la simulación sale de los servicios del backend, no de lo que le convendría a la prueba: GET /contenido devuelve categoria como objeto y GET /publico/:slug la aplana a una cadena, y simular las dos iguales dejó la pantalla pública en blanco la primera vez. El defecto estaba en la simulación —pero una simulación que no se parece a la API deja pasar exactamente eso en el otro sentido.

5.9 Lo que este frontend todavía no tiene

Qué falta Detalle
El color de marca no se aplica en ninguna parte La pantalla del perfil deja elegir entre tres temas y los guarda en el servidor, y la API los devuelve en el perfil público, pero ninguna pantalla de React los usa: el frontend original sí lo hacía. Es la parte del RF-12 que queda pendiente.
Todas las pantallas comparten el título de la pestaña El original tenía un archivo .html por pantalla, cada uno con su título. Bajo React el título sale del único index.html, así que el historial y las pestañas del navegador dicen lo mismo en todas. La página del código QR es la excepción: el servidor le inyecta el título del negocio y React no lo toca.
Safari de verdad El proyecto Móvil usa Chromium con el viewport y el user agent de un iPhone, porque este entorno no pudo instalar un WebKit real. Lo que se mide —media queries, cajas, contraste— no depende del motor; un fallo propio de WebKit sí se escaparía.
El doble paso de StrictMode, en el navegador Solo ocurre en desarrollo, y las de extremo a extremo corren contra el paquete compilado. Ese caso lo cubre Vitest.
